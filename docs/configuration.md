# Конфигурация Elira

Конфигурация — один TOML-файл, по умолчанию `elira.toml`. Путь задаётся флагом
`--config` у команд `run` и `check`:

```
elira run --config /etc/elira/elira.toml
elira check --config /etc/elira/elira.toml
```

`check` только читает файл, проверяет типы и валидацию и печатает число маршрутов
и upstream'ов; сокеты он не открывает.

`migrate` конвертирует подмножество nginx-конфига в TOML:

```
elira migrate /etc/nginx/nginx.conf > elira.toml
elira migrate --output elira.toml nginx.conf
```

Поддержаны `upstream` с `server` и `least_conn`, `server`/`listen`/`server_name`,
`location` с `proxy_pass`, `root` + `index`, `return`, `try_files`, `add_header`,
`auth_basic_user_file`, `allow`/`deny`, `client_max_body_size`, `gzip`,
`ssl_certificate`/`ssl_certificate_key`, `access_log` и регулярные `location`.
`if`, `rewrite`, переменные и вложенные `location` не переносятся, а печатаются
предупреждением в stderr; вход не теряется, но результат надо прочитать
глазами. Несколько `server` в одном файле дают предупреждение: у Elira один
`listen`.

Конфиг можно разбить на файлы:

```toml
include = ["/etc/elira/conf.d/*.toml"]
```

`include` — строка или массив; поддерживается один `*` в имени файла.
Пути относительны каталога включающего файла. `[[routes]]` и `[[upstreams]]`
дописываются, таблицы сливаются по ключам, скаляры из include перекрывают
родительские. Вложенность ограничена 16 уровнями.

В значениях подставляется окружение: `${VAR}` и `${VAR:-default}`. `$$`
означает литеральный `$`. Неизвестная переменная без default — ошибка
загрузки, а не пустая строка.

Все структуры объявлены с `deny_unknown_fields`: неизвестное поле — ошибка разбора,
а не молча проигнорированная опечатка. `max_connection` вместо
`max_connections` не даст серверу стартовать, и это сделано намеренно. Ошибка
разбора печатается с путём к файлу.

Перезагрузка — `SIGHUP`: сервер заново читает файл, собирает новое состояние и
подменяет его атомарно. Если новый файл не проходит разбор или валидацию, в лог
пишется ошибка, а старый конфиг продолжает работать. Что применяется сразу, а что
требует рестарта, разобрано в разделе «Ограничения и поведение».

`listen_unix` поднимает второй слушатель на файловом сокете. TLS, PROXY
protocol и `sendfile` на нём не применяются; peer для логов и ACL —
`127.0.0.1`. Сокет не удаляется при старте: существующий файл означает
ошибку, а не молчаливую замену чужого сокета.

Адреса везде имеют вид `IP:порт` (тип `SocketAddr` в TOML-строке), поэтому
`localhost:8080` не подходит — нужен `127.0.0.1:8080` или `[::1]:8080`.
Исключение — `servers` у upstream'ов и `allow` у `connect`: там допустимы
имена хостов.

## Верхний уровень

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `listen` | `IP:порт` | нет, обязательно | TCP-адрес основного HTTP-листенера |
| `listen_unix` | путь | нет | дополнительный HTTP/1.1 на unix-сокете |
| `h2c` | bool | `false` | HTTP/2 prior knowledge без TLS |
| `workers` | 1..64 | `1` | процессы-воркеры с SO_REUSEPORT; нужен `reuse_port = true` |
| `proxy_protocol` | bool | `false` | ждать PROXY protocol (v1/v2) на каждом соединении |
| `reuse_port` | bool | `false` | SO_REUSEPORT; нужен для hot restart по SIGUSR2 |
| `sendfile` | bool | `true` | zero-copy статика на Linux через `sendfile(2)` |
| `server_header` | bool | `true` | отдавать `Server: elira` и сохранять заголовок upstream |
| `limits` | таблица | значения по умолчанию | лимиты соединений и заголовков |
| `tls` | таблица | нет (HTTP без TLS) | сертификат для TCP-листенера |
| `acme` | таблица | нет | Let's Encrypt через TLS-ALPN-01; вместо `[tls]` |
| `http3` | таблица | нет (HTTP/3 выключен) | отдельный QUIC-листенер |
| `log` | таблица | `text` | формат access-лога |
| `health` | таблица | выключено | активные проверки upstream'ов |
| `connect` | таблица | выключено | туннели `CONNECT` |
| `metrics` | таблица | нет (метрики выключены) | отдельный листенер Prometheus |
| `cache` | таблица | выключено | in-memory кэш ответов |
| `upstream_tls` | таблица | проверять системные корни | настройки TLS до upstream'ов |
| `upstreams` | массив таблиц | пусто | группы бэкендов |
| `routes` | массив таблиц | обязательно, не пусто | таблица маршрутизации по Host |

`routes` — единственное обязательное поле помимо `listen`. Пустой массив
отклоняется с ошибкой `no routes configured`.

`sendfile` включает быстрый путь для статики: первый запрос на открытом
HTTP/1.1-соединении подглядывается до hyper, и простой `GET`/`HEAD` файла
отдаётся системным `sendfile(2)` без копирования через userspace. Быстрый
путь не используется для `Range`, `If-None-Match`, `If-Modified-Since`,
`Upgrade`, при наличии предсжатого `.br`/`.gz`, а также если у маршрута есть
`add_headers`/`remove_headers`, выключен `server_header` или задан
`Alt-Svc` — всё это уходит в hyper. Работает только на Linux.

`proxy_protocol` включает разбор заголовка PROXY до TLS и до HTTP. Поддержаны
версии 1 и 2. Заголовок при этом обязателен: соединение без него закрывается
без ответа. Включайте только тогда, когда порт доступен исключительно через
балансировщик — иначе клиент подделает свой адрес, а он попадает в логи,
`X-Forwarded-For` и rate limiter. Заголовок читается с `peek`, поэтому первые
байты HTTP не съедаются при ошибке.

## `[limits]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `max_headers` | целое > 0 | `64` | максимум заголовков в запросе (HTTP/1.1) |
| `max_header_bytes` | целое ≥ 8192 | `16384` (16 КиБ) | предел буфера заголовков |
| `upstream_timeout_secs` | целое, секунды | `30` | таймаут запроса к upstream |
| `max_connections` | целое > 0 | `1024` | одновременные клиентские соединения |
| `idle_timeout_secs` | целое, секунды | `60` | закрытие простаивающего keep-alive соединения |
| `max_body_bytes` | целое ≥ 0 | `0` | `413`, если `Content-Length` больше; `0` — без лимита |
| `requests_per_second` | целое ≥ 0 | `0` | токенов в секунду на IP; `0` — лимит выключен |
| `burst` | целое ≥ 0 | `0` | запас токенов; `0` — равен `requests_per_second` |
| `trusted_proxies` | список CIDR | `[]` | кому разрешено дополнять `X-Forwarded-For` |
| `request_body_timeout_secs` | целое, секунды | `30` | закрыть клиента, который перестал присылать тело; `0` выключает |
| `upstream_body_timeout_secs` | целое, секунды | `30` | прервать upstream, который перестал отдавать тело |
| `websocket_idle_secs` | целое, секунды | `3600` | закрыть websocket/CONNECT после простоя; `0` выключает |
| `max_response_bytes` | целое > 0 | `67108864` | предел потокового ответа FastCGI/CGI |
| `fastcgi_pool_idle` | целое ≥ 0 | `16` | idle-соединений FastCGI на бэкенд |
| `fastcgi_pool_idle_secs` | целое | `30` | TTL idle-соединения FastCGI |
| `response_buffer_bytes` | целое ≥ 0 | `0` | буферизовать ответ upstream до этого размера; `0` — потоком |

Подробности:

- `max_headers` передаётся в `http1::Builder::max_headers`. На HTTP/2 и HTTP/3 он
  не действует: там ограничение задаётся размером списка заголовков.
- `max_header_bytes` работает как `max_buf_size` для HTTP/1.1 и как
  `max_header_list_size` для HTTP/2. Слишком большой запрос получает `431`.
  Значение меньше `8192` отклоняется при загрузке: hyper не умеет работать с
  буфером меньше и паниковал бы внутри каждого соединения.
- `upstream_timeout_secs` ограничивает ожидание ответа upstream'а, установку
  соединения для `CONNECT` и для `Upgrade`, а также запись заголовков в
  upstream при upgrade. По истечении — `504 Gateway Timeout` (для туннелей —
  `502`).
- `max_connections` — семафор в цикле accept. При достижении лимита новый сокет
  просто закрывается, без ответа и без очереди; событие пишется в лог на уровне
  `debug`. То же число независимо ограничивает количество одновременных
  туннелей (`CONNECT` и `Upgrade`): у них свой семафор с этим же значением.
- `idle_timeout_secs` закрывает keep-alive соединение, если по нему не пришло
  ни одного запроса за указанное время. `0` отключает этот таймер полностью.
  Таймер сбрасывается в момент прихода запроса, а не окончания ответа.
- `max_body_bytes` проверяет только `Content-Length`. Тело, пришедшее chunked,
  этим лимитом не ограничивается: для него нужно буферизовать поток.
- `requests_per_second` включает token bucket на каждый IP. Превышение даёт
  `429` с `Retry-After: 1`. `burst` — глубина ведра; при `0` она равна
  `requests_per_second`.
- `trusted_proxies` — CIDR-блоки. Если peer входит в список, его
  `X-Forwarded-For` сохраняется и дополняется адресом peer'а. Для всех
  остальных заголовок заменяется адресом peer'а, а клиентские
  `X-Forwarded-*`/`Forwarded` отбрасываются.
- Жёстко зашиты и не настраиваются: 30 с на чтение заголовков HTTP/1.1,
  10 с на TLS-handshake, 5 с на connect к upstream, 30 с на idle в пуле
  соединений, 5 с на дозавершение соединения при остановке.

## `[compression]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `enabled` | bool | `true` | сжатие, если клиент прислал `Accept-Encoding` |
| `min_bytes` | целое | `1024` | не сжимать тела меньше этого размера |

Статика сжимается на лету теми же настройками, если рядом нет предсжатого
`.br`/`.gz`; для `Range` и `HEAD` сжатие не применяется. Сжимаются только
`200 OK` с типом `text/*`, `application/json`,
`application/javascript`, `application/xml`, `application/rss+xml`,
`application/atom+xml`, `image/svg+xml`. Исключения: `HEAD`, `206`, `304`,
ответы с уже выставленным `Content-Encoding`.

Предпочитается `br`, если клиент его принимает, иначе `gzip`. При сжатии
выставляется соответствующий `Content-Encoding`, добавляется
`Vary: Accept-Encoding`, а `Content-Length` снимается: тело идёт chunked.
Сжатие потоковое, поэтому заранее длину ответа посчитать нельзя.

## `[tls]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `cert` | путь | нет, обязательно | PEM-цепочка сертификатов |
| `key` | путь | нет, обязательно | PEM-приватный ключ |
| `client_ca` | путь | нет | PEM-корни для проверки клиентских сертификатов |
| `client_auth` | `off` \| `optional` \| `required` | `off` | запрашивать ли клиентский сертификат |
| `min_version` | `tls12` \| `tls13` | `tls12` | минимальная версия TLS |
| `ocsp` | путь | нет | DER OCSP-ответ для stapling; перечитывается по SIGHUP |
| `ocsp_hook` | путь | нет | команда, обновляющая `ocsp`; после неё идёт reload |
| `ocsp_refresh_secs` | целое > 0 | `86400` | период вызова `ocsp_hook` |
| `certificates` | массив таблиц | `[]` | дополнительные сертификаты по SNI |

Элемент `certificates`:

| Поле | Тип | Обязательно | Что делает |
| --- | --- | --- | --- |
| `cert` | путь | да | PEM-цепочка |
| `key` | путь | да | PEM-ключ |
| `names` | массив строк | да | точные имена или `*.example.com` |

Секция включает TLS на основном TCP-листенере. Если `[tls]` нет, тот же порт
обслуживает обычный HTTP; отдельного «редиректа на HTTPS» нет, и один порт не
может одновременно принимать и TLS, и открытый HTTP.

- Пара `cert`/`key` необязательна, если задан `certificates`: она служит
  сертификатом по умолчанию для клиентов без SNI. Без пары и без
  `certificates` загрузка падает.
- Имена в `certificates` не повторяются. `*.example.com` совпадает ровно с
  одним уровнем (`a.example.com`), но не с `a.b.example.com` и не с самим
  `example.com`. Если SNI не совпал, берётся сертификат по умолчанию.
- Отсутствующие файлы и битый PEM — ошибка сборки runtime, то есть до accept.
- ALPN предлагается в порядке `h2`, затем `http/1.1`. Клиент, поддерживающий
  оба, получит HTTP/2. HTTP/1.1 остаётся для клиентов без h2.
- `client_auth = "optional"` принимает клиентский сертификат, если он прислан
  и валиден, но пускает и без него. `required` без сертификата не пускает.
  Оба режима требуют `client_ca`; при `off` файл не читается вовсе.
- mTLS и SNI-сертификаты действуют и на QUIC-слушателе: `client_ca`,
  `client_auth` и `certificates` задаются в `[http3]` независимо от `[tls]`.
- Сертификат и ключ перечитываются по `SIGHUP`. Уже установленные соединения
  остаются на старом сертификате, новые используют новый. Если новые файлы
  битые, reload не применяется и работает старый конфиг.
- Приватный ключ в PEM распознаётся в вариантах, которые понимает
  `rustls-pemfile` (PKCS#8, PKCS#1, SEC1).

## `[acme]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `domains` | массив строк | обязателен | домены для сертификата |
| `contacts` | массив строк | обязателен | контакты ACME, `mailto:...` |
| `cache_dir` | путь | обязателен | кэш сертификатов и аккаунта |
| `production` | bool | `false` | `true` — Let's Encrypt, `false` — staging |
| `challenge` | `tls_alpn_01` \| `http_01` \| `dns_01` | `tls_alpn_01` | способ валидации |
| `http01_listen` | `IP:порт` | нет | отдельный plain-HTTP листенер для HTTP-01 |
| `dns_hook` | путь | нет | команда, публикующая TXT для DNS-01 |
| `dns_cleanup_hook` | путь | нет | команда, удаляющая TXT после валидации |
| `dns_propagation_secs` | целое | `30` | пауза после hook перед валидацией |

Сертификат получается по TLS-ALPN-01 прямо на основном TLS-листенере: порт
80 не нужен, но 443 должен быть доступен извне. `[acme]` и `[tls]` вместе —
ошибка. Сертификат продлевается в фоне; перезапуск не требуется.

Механизм проверен против Let's Encrypt staging и production на публичном
домене через реальный порт 443; staging удобен для проверки конфигурации без
production-лимитов. HTTP-01 требует, чтобы `listen` был на порту 80 либо был
задан `http01_listen`; токен отдаётся по
`/.well-known/acme-challenge/<token>` без TLS.

DNS-01 работает через внешний hook и поддерживает wildcard-имена. Команда
получает `DOMAIN`, `TXT_NAME`, `TOKEN` и `VALUE` в окружении и должна
опубликовать TXT-запись `TXT_NAME = VALUE`. После успешного exit Elira ждёт
`dns_propagation_secs`, затем просит CA проверить запись. Если задан
`dns_cleanup_hook`, после успешной выдачи он получает то же окружение плюс
`ACTION=cleanup` и должен удалить TXT-запись. Учётные данные
аккаунта и сертификат кэшируются в `cache_dir`; обновление проверяется раз
в 12 часов.

## `[upstream_tls]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `insecure` | bool | `false` | не проверять сертификат и hostname upstream'а |
| `ca` | путь | нет | дополнительный PEM-корень к системным |
| `http2` | bool | `false` | предлагать `h2` в ALPN; HTTP/1.1 остаётся |
| `min_version` | `tls12` \| `tls13` | `tls12` | минимальная версия TLS до upstream |

Применяется ко всем upstream'ам с `tls = true`. `insecure` нужен только для
внутренних self-signed бэкендов. С `http2 = true` ALPN предлагает `h2` и
`http/1.1`; выбор делает upstream.

## `[http3]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `listen` | `IP:порт` | нет, обязательно | UDP-адрес QUIC-листенера |
| `cert` | путь | нет, обязательно непустое | PEM-сертификат для QUIC |
| `key` | путь | нет, обязательно непустой | PEM-ключ для QUIC |
| `client_ca` | путь | нет | PEM-корни клиентских сертификатов |
| `client_auth` | `off` \| `optional` \| `required` | `off` | клиентские сертификаты на QUIC |
| `certificates` | массив таблиц | `[]` | SNI-сертификаты на QUIC, формат как у `[tls]` |

HTTP/3 живёт на отдельном UDP-порту и не делит сокет с TCP-листенером.
`cert`/`key` здесь независимы от `[tls]`: их можно не задавать в `[tls]` вовсе,
если по TCP отдаётся открытый HTTP. Оба поля обязательны — при пустом значении
загрузка падает с `http3.cert must not be empty` / `http3.key must not be empty`.

- QUIC использует ALPN `h3`; других протоколов на этом сокете нет.
- Маршрутизация, проксирование, статика, access-лог и `CONNECT` те же, что и на
  TCP: h3-слушатель получает тот же `Proxy`. Отличие — отсутствие
  `Transfer-Encoding` и `Content-Length` в ответах: во фрейминге HTTP/3 они не
  нужны.
- По `SIGHUP` слушатель останавливается и поднимается заново с новым
  сертификатом. Живые QUIC-соединения при этом рвутся — в отличие от HTTP/1.1 и
  HTTP/2 на TCP, которые переживают reload.
- Если h3-сертификат битый, задача слушателя завершается с ошибкой в логе;
  остальной сервер продолжает работать, но HTTP/3 не поднимется до следующего
  успешного reload или рестарта.
- Лимиты `max_headers`/`max_header_bytes` к h3 не применяются: слушатель их не
  читает.
- PROXY protocol v2 на QUIC разбирается до передачи датаграмм в quinn;
  транспортный peer остаётся адресом балансировщика, а адрес клиента из
  заголовка используется для логов, ACL и `X-Forwarded-For`.

## `[log]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `format` | `"text"` или `"json"` | `"text"` | формат строки access-лога |
| `template` | строка | нет | nginx-подобный шаблон; сильнее `format` |
| `syslog` | путь | нет | Unix datagram, обычно `/dev/log` |

Значение сравнивается точно: только эти две строки. Любое
другое (включая `Text` или `JSON`) даёт ошибку `unknown log format "...", expected "text" or "json"`.
Формат читается на каждый запрос из текущего runtime, поэтому смена по `SIGHUP`
применяется и к уже открытым keep-alive соединениям.

Без `file` и `syslog` access-лог пишется в target `access` через `tracing`:
одна строка на запрос, с id запроса, методом, версией, Host, путём, статусом,
размером тела и временем. Формат `json` — та же запись в виде JSON-объекта.

Шаблон понимает `$remote_addr`, `$host`, `$request`, `$request_method`,
`$request_uri`, `$server_protocol`, `$status`, `$body_bytes_sent`,
`$http_user_agent`, `$http_referer`, `$request_time`, `$request_id`,
`$time_iso8601` и `$time_local`. Неизвестная переменная — ошибка загрузки,
литеральный доллар пишется как `$$`. Время сейчас всегда UTC.

## `[health]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `enabled` | bool | `false` | включает активные проверки |
| `path` | строка | `"/health"` | путь, который опрашивается на каждом upstream |
| `interval_secs` | целое > 0 | `5` | период между циклами проверок |
| `timeout_secs` | целое > 0 | `2` | таймаут на каждую операцию проверки |

Проверка — обычный HTTP/1.1 `GET path` с `Connection: close` на адрес
`servers` из upstream'а. Живым считается любой ответ `2xx` или `3xx`; всё
остальное, ошибка соединения и таймаут — «down».

- `path` должен начинаться с `/` и не содержать пробелов и управляющих
  символов; иначе ошибка `health.path must start with '/' ...`. Проверка пути
  выполняется только при `enabled = true`.
- `interval_secs` и `timeout_secs` тоже проверяются только при включённых
  проверках; ноль — ошибка.
- `timeout_secs` применяется отдельно к connect, записи запроса и чтению ответа,
  поэтому худший случай одной проверки — примерно три таймаута.
- `upstream` без health-проверок (или выключенные проверки) считаются живыми:
  сервер получает трафик, пока не начнёт отвечать ошибками на сами запросы.
- Fail-open: если проверка пометила down все серверы upstream'а, трафик всё
  равно идёт на один из них (по кругу), а не превращается в `503`. Один сломанный
  пробник не должен устраивать аварию.
- Down-сервер исключается из round-robin до следующей успешной проверки; обратно
  он возвращается сам, без рестарта.
- При выключенных проверках цикл просыпается раз в 30 с, ничего не опрашивает и
  считает все серверы живыми; метрики с числами up/down обновляются на каждом
  таком тике.
- По `SIGHUP` конфиг health применяется сразу, и перед публикацией нового
  runtime все upstream'ы проверяются один раз — чтобы после reload не было окна,
  в котором всё снова «здорово».

## `[connect]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `enabled` | bool | `false` | разрешает метод `CONNECT` |
| `allow` | массив строк | `[]` | точные `host:port`, куда разрешён туннель |

При `enabled = false` любой `CONNECT` получает `405 Method Not Allowed`.
При `enabled = true` список `allow` обязателен и не может быть пустым.

- Каждый элемент — ровно `host:port`, с портом. `10.0.0.5` без порта
  отклоняется, как и строка с `@` (userinfo) или `/`. IPv6 — в скобках:
  `[::1]:5432`.
- Сравнение с целью запроса — точное совпадение строки authority. Это не
  подсеть и не шаблон: `api.internal:443` не откроет `10.0.0.5:443` и не
  покроет другой порт.
- Почему это опасно: включённый без ограничений `CONNECT` превращает
  reverse-proxy в открытый релей, через который из интернета ходят во внутреннюю
  сеть и на localhost (SSRF-плечо). Обратному прокси такой режим обычно не нужен
  вовсе, поэтому по умолчанию он выключен. Список `allow` — единственная защита,
  других проверок назначения нет.
- Туннели ограничены тем же числом, что `limits.max_connections`, и тем же
  `upstream_timeout_secs` на установку соединения.
- По README `CONNECT` работает только по HTTP/1.1.

## `[metrics]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `listen` | `IP:порт` | нет, обязательно | адрес отдельного HTTP-листенера метрик |
| `auth_file` | путь | нет | htpasswd; закрывает весь админский листенер |

Секция включает отдельный мини-листенер. `GET /metrics` отдаёт счётчики в
текстовом формате Prometheus (`text/plain; version=0.0.4`). `GET /status`
отдаёт JSON с upstream'ами, их серверами, health-флагами, числом активных
запросов и статистикой кэша.

| Метод и путь | Что делает |
| --- | --- |
| `GET /metrics` | счётчики Prometheus |
| `GET /status` | JSON-снимок |
| `POST /reload` | то же, что `SIGHUP` |
| `POST /drain` | graceful shutdown |
| `POST /cache/purge` | очистить кэш |

Любой другой путь или метод — `404`. Основной листенер эти пути не
обслуживает.

- Здесь нет TLS, лимитов соединений и таймаутов из `[limits]`.
- Слушайте loopback (`127.0.0.1:9090`), если счётчики не должны быть видны
  снаружи. `auth_file` включает Basic auth для всех путей, включая `/metrics`.
- Адрес фиксируется при старте. Изменение `metrics.listen` по `SIGHUP`
  игнорируется с предупреждением в логе; добавление или удаление секции тоже
  требует рестарта.

## `[cache]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `enabled` | bool | `false` | кэш успешных `GET` |
| `ttl_secs` | целое | `60` | время жизни записи |
| `max_bytes` | целое | `67108864` (64 МиБ) | суммарный размер тел |
| `max_item_bytes` | целое | `1048576` (1 МиБ) | максимальное тело одной записи |
| `dir` | путь | нет | хранить тела на диске в этом каталоге |
| `stale_secs` | целое ≥ 0 | `0` | отдавать протухшее тело, пока идёт обновление |

Кэшируются только `200 OK` на `GET` с известным `Content-Length` не больше
`max_item_bytes`, без `Set-Cookie` и без `Cache-Control: no-store/private`.
Ответы с неизвестной длиной не кэшируются: тело не буферизуется.

Ключ — нормализованный Host плюс путь с query. Ответ кэша отдаётся без
сжатия. `X-Cache` принимает `HIT`, `MISS` или `STALE`. Вытеснение: сначала
протухшие записи, затем самые старые по времени вставки.

`Vary` учитывается: под ключом хранится по записи на каждую комбинацию
заголовков. Запросы с `Authorization`/`Cookie` кэш обходят, ответы с
`Set-Cookie`, `no-store`, `private` и `no-cache` не сохраняются.
`s-maxage`/`max-age` сокращают `ttl_secs`, но не удлиняют его; на ответе
выставляется `Age`.

С `stale_secs > 0` протухшая запись ещё отдаётся с `X-Cache: STALE`, а в фоне
запускается один запрос за свежей копией. Запрос условный: сохранённые `ETag`
и `Last-Modified` уходят как `If-None-Match`/`If-Modified-Since`, ответ `304`
продлевает TTL без повторной передачи тела. На время обновления ключ помечен,
поэтому параллельные запросы не создают лавину. Кэшированный ответ на HIT
проходит то же сжатие, что и свежий.

С `dir` тела лежат в файлах вместе с метаданными, а в памяти остаются только
индексы. Записи переживают перезапуск: протухшие и битые файлы удаляются при
загрузке, бюджет `max_bytes` применяется сразу. Один файл на запись;
`max_bytes` по-прежнему считает тела, а не файловые блоки.

## `[[upstreams]]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `name` | строка | нет, обязательна | имя, на которое ссылаются маршруты |
| `servers` | массив строк | нет, обязателен и непуст | адреса бэкендов `host:port` или `unix:/path` |
| `balance` | `round_robin` \| `least_conn` | `round_robin` | как выбирать сервер |
| `retries` | целое 0..5 | `0` | дополнительные попытки на ошибку соединения |
| `tls` | bool | `false` | подключаться к серверам по HTTPS |
| `sni` | строка | нет | имя для SNI и проверки сертификата |
| `health_path` | путь | `health.path` | свой путь health-пробы |
| `tls_insecure` | bool | `[upstream_tls] insecure` | не проверять сертификат |
| `tls_ca` | путь | `[upstream_tls] ca` | свой PEM-корень |
| `http2` | bool | `[upstream_tls] http2` | предлагать `h2` |
| `dns_ttl_secs` | целое > 0 | `30` | предел жизни соединения в пуле; имя резолвится заново при новом соединении |

- `name` не может быть пустым или повторяться.
- `servers` не может быть пустым; каждый элемент — `host:port` с портом
  или `unix:/абсолютный/путь.sock`. Допустимы DNS-имена и IP; IPv6 — в
  скобках. Строки с `@` или `/` без префикса `unix:` отклоняются.
- Unix-сокет говорит по HTTP/1.1 без TLS. `tls = true` вместе с `unix:` —
  ошибка загрузки.
- `round_robin` идёт по кругу, пропуская серверы, помеченные health-проверкой
  как мёртвые. `least_conn` выбирает живого с наименьшим числом активных
  запросов; счётчик держится от приёма запроса до возврата заголовков ответа,
  поэтому потоковое тело в нём уже не учитывается.
- `retries` работает только для `GET`, `HEAD` и `OPTIONS` без
  `Content-Length` и `Transfer-Encoding`: тело нельзя переиграть. Повтор
  происходит при ошибке соединения или таймауте, не при ответе 5xx — бэкенд
  мог уже начать обработку.
- Все серверы помечены мёртвыми — трафик всё равно идёт (fail-open), иначе
  сломанная проверка превратилась бы в простой.
- Hyper резолвит имя при каждом новом соединении. `dns_ttl_secs` ограничивает
  время жизни соединения в пуле, поэтому смена DNS видна не позже этого
  значения (по умолчанию 30 секунд).
- С `tls = true` соединение идёт по HTTPS; `sni` нужен, когда в `servers` стоит
  IP, а сертификат выписан на имя. Health-проба для TLS-бэкенда делает настоящее
  рукопожатие теми же настройками доверия; для unix-сокета проба идёт по нему.
- Health-флаги сбрасываются при сборке нового runtime, но при включённых
  проверках reload сначала опрашивает серверы, а потом публикует новое
  состояние.
- Один upstream можно использовать в нескольких маршрутах.
- Health-флаги сбрасываются при сборке нового runtime, но при включённых
  проверках reload сначала опрашивает серверы, а потом публикует новое
  состояние.
- Один upstream можно использовать в нескольких маршрутах.

## `[[routes]]`

| Поле | Тип | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `host` | строка | нет, обязателен | `example.com`, `*.example.com` или `*` |
| `path` | строка | `/` | префикс пути; побеждает самый длинный |
| `path_regex` | строка | нет | regex по пути; проверяется после префиксов |
| `fastcgi_pass` | строка | нет | `host:port` или `unix:/path` |
| `fastcgi_root` | путь | нет | корень для `SCRIPT_FILENAME` |
| `fastcgi_index` | строка | `index.php` | файл для пути с `/` на конце |
| `cgi_pass` | путь | нет | абсолютный путь к CGI-скрипту |
| `module` | путь | нет | абсолютный путь к `.so`-модулю |
| `module_sandbox` | bool | `false` | запускать модуль в дочернем процессе |
| `upstream` | строка | нет | имя upstream'а для проксирования |
| `root` | путь | нет | каталог со статикой |
| `redirect` | таблица | нет | `{ to, status }`; вместо upstream и root |
| `index` | массив строк | `["index.html"]` | файлы, которые ищутся для каталога |
| `spa` | bool | `false` | отдавать index для несуществующих путей |
| `strip_prefix` | bool | `false` | срезать `path` перед отправкой в upstream |
| `add_headers` | массив строк | `[]` | заголовки ответа в виде `Name: value` |
| `remove_headers` | массив строк | `[]` | заголовки ответа, которые надо убрать |
| `try_files` | массив строк | `[]` | кандидаты, если путь не найден; `$uri` подставляется |
| `autoindex` | bool | `false` | генерировать листинг каталога |
| `auth_file` | путь | нет | htpasswd с bcrypt-хешами |
| `ip_allow` | массив CIDR | `[]` | кому разрешено; пусто — всем |
| `ip_deny` | массив CIDR | `[]` | кому запрещено; сильнее `ip_allow` |
| `timeout_secs` | целое > 0 | `limits.upstream_timeout_secs` | таймаут ответа upstream'а для этого маршрута |
| `requests_per_second` | целое > 0 | глобальный лимит | свой token bucket для маршрута |
| `burst` | целое ≥ 0 | равен rate | глубина bucket'а маршрута |
| `max_body_bytes` | целое ≥ 0 | глобальный лимит | свой предел `Content-Length` |
| `max_response_bytes` | целое > 0 | `limits.max_response_bytes` | свой предел потокового ответа |
| `max_concurrent` | целое > 0 | `16` | одновременные FastCGI/CGI/module запросы |
| `error_pages` | массив строк | `[]` | `"404 /404.html"` |
| `error_root` | путь | `root` | каталог для страниц ошибок проксирующего маршрута |

Правила:

- Нужна ровно одна цель: `upstream`, `root`, `redirect`, `fastcgi_pass`,
  `cgi_pass` или `module`. Две сразу — ошибка, ни одной — `route N needs
  exactly one`.
- `module_sandbox` запускает `.so` в дочернем процессе `elira
  module-worker`; путь к раннеру можно переопределить `ELIRA_MODULE_RUNNER`.
  Это изоляция падений и FFI-ошибок, но не смена пользователя и не namespace:
  дочерний процесс сохраняет права сервера.
- `fastcgi_pass` требует `fastcgi_root`; `SCRIPT_FILENAME` собирается из
  корня, пути запроса и `fastcgi_index` для каталога. `cgi_pass` и `module`
  должны быть абсолютными путями. Модуль загружается при старте и работает
  в процессе сервера.
- FastCGI и CGI передают тело запроса и ответа потоком с backpressure;
  `max_response_bytes` ограничивает ответ, `max_concurrent` — число
  одновременных app-запросов. Модули `.so` загружаются только с
  не-world-writable пути.
- `ocsp_hook` выполняется при старте (до сборки TLS) и затем раз в
  `ocsp_refresh_secs`; после успешного обновления файла конфиг
  перезагружается, и новый ответ попадает в stapling. При `workers > 1` hook
  запускает супервизор и рассылает SIGHUP воркерам.
- `workers > 1` запускает супервизор и N процессов; каждый слушает тот же
  порт через `SO_REUSEPORT`. SIGUSR2 перезапускает воркеры по одному,
  SIGHUP рассылается всем и может добавить воркеров, если новое значение
  больше; уменьшение требует рестарта. Счётчики воркеров раз в секунду уходят
  супервизору по Unix datagram, и именно он отдаёт агрегированные `/metrics`
  и `/status` (снимок каждого воркера отдельно). `POST /reload` рассылает SIGHUP воркерам, `POST /drain`
  останавливает группу, `POST /cache/purge?prefix=host/path` будит очистку
  кэша во всех воркерах.
- `host` сравнивается без учёта регистра, без порта и без завершающей точки.
  `Example.COM:8080` попадёт в маршрут `example.com`. Host с userinfo
  (`admin:80@example.com`) и некорректным портом отклоняется с `400`.
- `host = "*.example.com"` совпадает с поддоменами (`api.example.com`), но не
  с самим `example.com`. Звёздочка допустима только в начале.
- `host = "*"` — маршрут по умолчанию. Таких может быть несколько, если у них
  разные `path`; повтор пары `(host, path)` — ошибка `route for host ... is
  defined twice`.
- `path` — префикс, а не регулярка. `/api` совпадает с `/api` и `/api/users`,
  но не с `/apix`. Внутри одного host выбирается самый длинный подходящий
  префикс; маршрут без `path` играет роль `/`.
- `path_regex` проверяется после всех префиксных маршрутов того же host.
  `path` и `path_regex` взаимоисключающие; с regex нельзя использовать
  `strip_prefix`. Битое выражение отклоняется при загрузке.
- `strip_prefix` (только с `upstream`) убирает совпавший префикс:
  `/api/users` при `path = "/api"` уходит на бэкенд как `/users`.
- `redirect` отвечает `301`, `302`, `303`, `307` или `308` с `Location` из
  `to`, не трогая upstream. Другие статусы отклоняются при загрузке.
- `add_headers` и `remove_headers` применяются к ответу после проксирования
  или статики. Формат `add_headers` — `"Name: value"`; строка без двоеточия
  или с невалидным именем отклоняется.
- `index` — имена файлов, а не пути: элемент не может быть пустым, содержать
  `/` или `..`. Для каталога файлы перебираются по порядку. Запрос каталога
  без завершающего `/` получает `301`.
- `spa = true` отдаёт первый файл из `index` для путей, которых нет на диске.
  Если `index = []`, комбинация отклоняется.
- `index` и `spa` имеют смысл только вместе с `root`.
- Статика обслуживает только `GET` и `HEAD`, остальные методы получают `405`.
  Выход за пределы `root` через `..` и симлинки запрещён.
- `auth_file` включает HTTP Basic: без верных данных — `401` и
  `WWW-Authenticate: Basic realm="elira"`. Пароли проверяются bcrypt.
- `ip_allow`/`ip_deny` сравнивают адрес peer'а (с учётом PROXY protocol).
  `ip_deny` проверяется первым. Отказ — `403`.
- Маршруты с `auth_file` или ACL не используют zero-copy `sendfile`:
  проверка доступа должна пройти в общем пути.
- `timeout_secs` переопределяет общий таймаут для запросов этого маршрута.
  Ноль отклоняется при загрузке. Истёкший таймаут — `504`.
- `requests_per_second`/`burst` создают отдельный limiter на маршрут; отказ —
  `429`. `max_body_bytes` проверяет `Content-Length` до обращения к upstream.
- `error_pages` подменяет тело ответа с указанным статусом файлом. Статус
  сохраняется, даже если файл существует. `error_root` нужен, когда маршрут
  проксирует, а не отдаёт статику.

## Ограничения и поведение

Что делает `SIGHUP`:

| Что | Поведение |
| --- | --- |
| `upstreams`, `routes` | применяются сразу; следующий запрос видит новую таблицу |
| `limits.*` таймауты, `routes`, `upstreams` | применяются сразу |
| `log.format` | применяется сразу, включая открытые keep-alive соединения |
| `health.*` | применяется, затем один внеочередной цикл проверок |
| `connect.*` | применяется сразу |
| `tls.cert`, `tls.key` | перечитываются; новые соединения — с новым сертификатом |
| `http3.*` | слушатель перезапускается, живые QUIC-соединения рвутся |
| `listen` | не меняется, в лог пишется `listen address changes need a restart` |
| `limits.max_connections`, `max_headers`, `max_header_bytes` | не меняются, предупреждение в логе |
| `limits.idle_timeout_secs` | не меняется и предупреждения не даёт: значение захвачено при старте |
| `metrics.listen`, наличие `[metrics]` | не меняются, предупреждение в логе |
| невалидный файл | reload отменяется, работает старый конфиг, в лог — ошибка |

Отдельно:

- `SIGHUP` перечитывает и TLS-материал, и h3-материал. Битый TLS-файл отменяет
  весь reload: старый конфиг продолжает работать. Битый h3-файл не мешает
  применить остальной конфиг, но h3-листенер после перезапуска не поднимется,
  и в лог уйдёт `http/3 listener stopped`.
- Добавление `[tls]`/удаление `[tls]` по reload технически меняет режим новых
  соединений на том же порту. На практике это не переключение «HTTP → HTTPS», а
  смена ожидаемого протокола на уже слушающем сокете: старые соединения
  доживают, новые должны угадать новый режим. Меняйте это рестартом.
- Соединения при остановке (SIGINT/SIGTERM) получают до 10 с на дозавершение
  запросов, затем до 5 с на graceful shutdown каждого соединения; после этого
  процесс выходит.
- `SIGUSR2` делает hot restart: запускает новый процесс того же бинарника и
  завершает текущий. Нужен `reuse_port = true`, иначе сигнал игнорируется.
  Новый процесс сразу биндит те же порты через `SO_REUSEPORT`; старый
  доживает 750 мс и уходит в обычный drain. HTTP/3-сокет также создаётся с
  `SO_REUSEPORT`.
- На не-Unix платформах reload и hot restart недоступны.

## Полный пример

Статика и прокси, TLS на TCP, HTTP/3 на UDP, health-проверки и метрики:

```toml
listen = "0.0.0.0:443"
proxy_protocol = true   # only when the port is reachable solely through the LB

[limits]
max_headers = 64
max_header_bytes = 16384
upstream_timeout_secs = 30
max_connections = 4096
idle_timeout_secs = 60
max_body_bytes = 8388608
requests_per_second = 100
burst = 200
trusted_proxies = ["10.0.0.0/8", "192.168.0.0/16"]

[compression]
enabled = true
min_bytes = 1024

[tls]
cert = "/etc/elira/fullchain.pem"
key = "/etc/elira/privkey.pem"

[http3]
listen = "0.0.0.0:443"
cert = "/etc/elira/fullchain.pem"
key = "/etc/elira/privkey.pem"

[log]
format = "json"

[health]
enabled = true
path = "/health"
interval_secs = 5
timeout_secs = 2

[connect]
enabled = false

[metrics]
listen = "127.0.0.1:9090"

[[upstreams]]
name = "app"
servers = ["127.0.0.1:3000", "127.0.0.1:3001"]
balance = "least_conn"
retries = 1

[[upstreams]]
name = "api"
servers = ["10.0.0.11:8080", "10.0.0.12:8080"]

[[routes]]
host = "*"
upstream = "app"

[[routes]]
host = "api.example.com"
upstream = "api"

[[routes]]
host = "static.example.com"
root = "/srv/www"
index = ["index.html"]
spa = false

[[routes]]
host = "spa.example.com"
root = "/srv/spa"
index = ["index.html"]
spa = true
```

Порты TCP и UDP могут совпадать (`443` в примере) — это разные сокеты.
Проверить файл перед запуском:

```
elira check --config elira.toml
```

## Частые ошибки

| Сообщение / симптом | Причина | Что делать |
| --- | --- | --- |
| `limits.max_header_bytes must be at least 8192` | буфер меньше 8192 | поднимите до 8192 или выше |
| `limits.max_headers must be greater than zero` | `max_headers = 0` | уберите ноль |
| `limits.max_connections must be greater than zero` | `max_connections = 0` | уберите ноль |
| `limits.trusted_proxies: "..." is not a CIDR block` | строка не парсится как сеть | формат `10.0.0.0/8` или `127.0.0.1/32` |
| `route N needs exactly one of \`upstream\` or \`root\`` | у маршрута нет цели | добавьте `upstream` или `root` |
| `route N has both \`upstream\` and \`root\`` | указаны обе цели | оставьте одну |
| `route N: index file "..." must be a plain file name` | `/` или `..` в `index` | пишите `index.html`, а не путь |
| `route N: \`spa\` needs at least one index file` | `spa = true` при `index = []` | оставьте хотя бы один файл |
| `connect.enabled requires a non-empty connect.allow list` | включили `CONNECT` без целей | перечислите точные `host:port` |
| `connect target "..." is not host:port` | нет порта, есть `@` или `/` | формат `host:port` |
| `upstream "..." has no servers` | пустой `servers` | добавьте адрес |
| `upstream "..." has N retries, the maximum is 5` | слишком много повторов | уменьшите до 5 |
| `upstream "...": "..." is not host:port` | адрес без порта | `127.0.0.1:3000` |
| `upstream "..." is defined twice` | повтор `name` | переименуйте |
| `route for host "..." is defined twice` | повтор `host` | объедините маршруты |
| `only one \`host = "*"\` route is allowed` | два default-маршрута | оставьте один `*` |
| `route N points to unknown upstream` | опечатка в имени | сверьте с `[[upstreams]].name` |
| `no routes configured` | нет `[[routes]]` | добавьте хотя бы один |
| `unknown field \`...\`` | опечатка в имени поля | проверьте имя по этому документу |
| `unknown log format "..." ...` | не `text` и не `json` | исправьте значение |
| `invalid socket address` / ошибка TOML на `listen` | имя хоста вместо IP | `127.0.0.1:8080`, `[::1]:8080` |
| `tls.cert is required...` / `tls.key is required...` | пустое поле в `[tls]` | укажите непустой путь |
| `tls.client_ca is required...` | `client_auth` включён без CA | добавьте `client_ca` или верните `off` |
| `http3.client_ca is required...` | `http3.client_auth` включён без CA | добавьте `http3.client_ca` |
| `acme HTTP-01 needs a listener on port 80 or acme.http01_listen` | HTTP-01 без порта 80 | задайте `http01_listen` |
| `cache.dir must not be empty` | пустой путь кэша | уберите поле или задайте каталог |
| `tls certificate name "..." is used twice` | одно имя в двух сертификатах | оставьте одно |
| `route N: "..." is not "STATUS /path"` | битая `error_pages` | формат `404 /404.html` |
| `route N: timeout_secs must be greater than zero` | нулевой таймаут | уберите поле или поставьте больше нуля |
| `http3.cert must not be empty` | `[http3]` без сертификата | задайте `cert` и `key` |
| `health.path must start with '/'...` | путь без `/` | `/health` |
| `health.interval_secs must be greater than zero` | ноль при `enabled = true` | поставьте `5` или больше |
| `cannot bind ...` на старте | порт занят или нет прав | смените `listen`/`metrics.listen` |
