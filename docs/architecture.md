# Архитектура Elira

Документ описывает путь запроса в текущем коде. Конфигурация разбирается в
`elira-config`, сетевой цикл живёт в `crates/elira/src/server.rs`, а решения о
маршруте и содержимом ответа принимает `elira-proxy`.

## Поток запроса

```
TCP accept
  -> PROXY protocol v1/v2 (если включён)
  -> TLS handshake + ALPN (если задан [tls])
       -> h2 или http/1.1
  -> hyper service
       -> ArcSwap<Runtime> загружается на запрос
       -> Proxy::handle
            -> rate limit по IP
            -> Router по Host
                 -> upstream: Pool, health, retries
                 -> static: Files
                 -> CONNECT / Upgrade
            -> заголовки ответа, сжатие, тело
       -> метрики TCP-пути и access-лог

UDP (QUIC)
  -> HTTP/3 listener
  -> тот же Proxy
  -> access-лог
```

## Приём соединения

`server::serve` принимает TCP-соединения и держит семафор на
`limits.max_connections`. При исчерпании лимита новый сокет закрывается без
ответа; событие пишется в лог на уровне `debug`. На каждое соединение
создаётся задача, которая освобождает permit после завершения.

Accept-ошибки не крутят цикл вхолостую: после ошибки цикл ждёт 100 мс и
продолжает работу.

## PROXY protocol

Если `proxy_protocol = true`, до TLS и до HTTP вызывается
`proxy_protocol::read_peer`. Заголовок читается через `peek`, поэтому при
ошибке первые байты HTTP не теряются. Поддержаны версии 1 и 2.

Заголовок обязателен: соединение без него или с битым заголовком закрывается
без ответа. Адрес из заголовка заменяет адрес сокета и дальше используется в
логах, rate limit и `X-Forwarded-For`.

## TLS и ALPN

Конфигурация TLS загружается из текущего `Runtime` при установке соединения,
то есть новые соединения после `SIGHUP` получают новый сертификат. Handshake
ограничен 10 секундами; клиент, который не прислал ClientHello, не держит
permit бесконечно.

rustls предлагает ALPN в порядке `h2`, затем `http/1.1`. HTTP/2 включается
только если клиент согласовал `h2`; cleartext HTTP/2 (h2c) не поддерживается.
Клиентские сертификаты не запрашиваются.

## HTTP/1.1 и HTTP/2

Оба протокола обслуживает hyper.

- HTTP/1.1: `max_headers`, `max_buf_size` из `limits`, таймаут чтения
  заголовков 30 секунд, поддержка `Upgrade` через `with_upgrades`.
- HTTP/2: `max_header_list_size` из `limits.max_header_bytes`, keep-alive
  interval 30 секунд и timeout 20 секунд.
- Idle watchdog закрывает keep-alive соединение, если запросов не было
  `limits.idle_timeout_secs`; ноль отключает таймер. Таймер сбрасывается при
  приходе запроса, а не при завершении ответа.
- При остановке сервера соединение получает `graceful_shutdown` и до 5 секунд
  на дозавершение.

## HTTP/3

HTTP/3 живёт на отдельном UDP-листенере (`[http3]`) и использует QUIC через
quinn и h3. ALPN только `h3`. Peer берётся из QUIC-соединения; PROXY protocol
на этом пути не разбирается.

Тело запроса перекладывается из QUIC-потока в `StreamBody` через канал, после
чего вызывается тот же `Proxy::handle`, что и на TCP. Из ответа удаляются
`Content-Length` и `Transfer-Encoding`: в HTTP/3 фрейминг задаёт поток.
Access-лог пишется, метрики TCP-листенера на этом пути не обновляются.

## Runtime и перезагрузка

`Runtime` содержит `Proxy`, TLS-конфигурацию, формат лога, настройки health и
`[http3]`. Он лежит в `ArcSwap` и загружается на каждый запрос, поэтому
`SIGHUP` применяется к следующему запросу на уже открытом keep-alive
соединении.

По `SIGHUP`:

1. Файл читается и валидируется заново; при ошибке остаётся старый runtime.
2. Собирается новый `Runtime`: перечитываются сертификаты, создаётся новый
   `Proxy` с маршрутами и upstream'ами.
3. Если health включён, upstream'ы проверяются один раз до публикации.
4. Новый runtime атомарно публикуется в `ArcSwap`.
5. HTTP/3-задача останавливается и запускается заново; живые QUIC-соединения
   при этом рвутся.

Адрес `listen`, `max_connections`, `max_headers`, `max_header_bytes`,
`idle_timeout_secs` и адрес metrics-листенера захвачены при старте. Их
изменение требует рестарта; для части полей в лог пишется предупреждение.

## Маршрутизация

`Proxy::handle` сначала проверяет rate limit по IP peer'а. Превышение даёт
`429` с `Retry-After: 1`.

Host берётся из `Host` или из `:authority` для HTTP/2. `canonical_host`
приводит его к нижнему регистру, убирает завершающую точку и порт. Host с
userinfo или неверным портом отклоняется с `400`. `Router` ищет точное
совпадение, затем маршрут `host = "*"`. Если маршрута нет, ответ `404`.

## Upstream

Каждый `[[upstreams]]` превращается в `Pool`: список адресов, флаги здоровья,
счётчики активных запросов и атомарный индекс.

- `round_robin` идёт по кругу и пропускает серверы, помеченные health-проверкой
  как мёртвые.
- `least_conn` выбирает живого сервера с наименьшим числом активных запросов.
  Счётчик держится от выбора сервера до возврата заголовков ответа.
- Если все серверы помечены мёртвыми, трафик всё равно идёт на один из них:
  fail-open, чтобы сломанный пробник не устроил аварию.
- `retries` добавляет попытки только для GET, HEAD и OPTIONS без
  `Content-Length` и `Transfer-Encoding`. Повтор бывает при ошибке соединения
  или таймауте; ответ `5xx` не повторяется.
- Соединение к upstream всегда открывается по `http`; TLS до бэкенда нет.
- Таймаут запроса — `limits.upstream_timeout_secs`; connect пула соединений
  ограничен 5 секундами, idle в пуле — 30 секундами. Ошибка даёт `502`,
  таймаут — `504`. Для `CONNECT` и `Upgrade` установка соединения ограничена
  тем же `upstream_timeout_secs`.

Перед отправкой удаляются hop-by-hop заголовки, токены из `Connection` и
клиентские forwarding-заголовки: `Forwarded`, `X-Forwarded-*`, `X-Real-IP`,
`X-Original-URL`, `X-Rewrite-URL` и underscore-алиасы. Затем выставляются
`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` и
`Via: 1.1 elira`.

Если peer входит в `limits.trusted_proxies`, его `X-Forwarded-For` сохраняется
и дополняется адресом peer'а. Для остальных цепочка начинается заново с адреса
peer'а.

## Статика

Маршрут с `root` обслуживает `Files`:

- только GET и HEAD; остальные методы получают `405` и `Allow`;
- путь percent-декодируется, сегмент `..` отклоняется, NUL и обратный слэш
  дают `400`;
- `root` и найденный файл канонизируются; файл за пределами `root` через
  симлинк получает `403`;
- каталог без завершающего `/` получает `301` с `Location`;
- для каталога перебираются `index`-файлы, затем работает SPA fallback, если
  `spa = true`;
- `ETag`, `If-None-Match` и `If-Modified-Since` дают `304`;
- поддерживается один byte range; несколько диапазонов отдаются целиком;
- выставляются `Content-Type`, `Content-Length`, `Accept-Ranges`,
  `Last-Modified` и `X-Content-Type-Options: nosniff`.

Ответ статики возвращается из `Files::serve` напрямую и не проходит через
ветку сжатия проксированных ответов.

## CONNECT и Upgrade

`CONNECT` выключен по умолчанию. При включении цель должна точно совпасть с
одним из `connect.allow`; иначе `403`. После установки TCP-соединения клиент
получает `200`, и байты копируются в обе стороны. Туннели ограничены тем же
числом, что `limits.max_connections`.

`Upgrade` (websockets и другие протоколы) не идёт через пул соединений: для
него открывается отдельный TCP-сокет к upstream'у, запрос сериализуется вручную,
читается ответ `101`, после чего работает `copy_bidirectional`. Запрос с телом
для `Upgrade` отклоняется с `400`.

## Ответ

Для проксированного ответа hop-by-hop заголовки и токены из `Connection`
удаляются. `Content-Length` upstream'а не копируется: framing строит hyper.
Добавляется `Server: elira`.

gzip включается, если:

- `compression.enabled` и клиент прислал `Accept-Encoding: gzip` с `q > 0`;
- статус `200`, метод не HEAD, `Content-Encoding` ещё не выставлен;
- тип содержимого сжимаемый, а известная длина не меньше `min_bytes`.

При сжатии выставляются `Content-Encoding: gzip` и `Vary: Accept-Encoding`,
тело идёт потоком. Кэша ответов в пути запроса нет: `elira-cache` сейчас
содержит только doc-комментарий и не используется.

## Логи и метрики

После ответа TCP-путь записывает статус и длительность в `Metrics`, затем
формирует `Entry` для access-лога: peer, метод, версия, Host, путь, статус,
размер, длительность, User-Agent и request id. Формат `text` или `json`
берётся из текущего runtime.

`Metrics` хранит счётчики в атомиках и рендерит текст Prometheus. Отдельный
листенер `[metrics]` отвечает `GET /metrics`; остальные пути и методы получают
`404`. У листенера нет TLS, лимитов и аутентификации.

Health-цикл просыпается раз в `health.interval_secs`, а при выключенных
проверках — раз в 30 секунд и ничего не опрашивает. При включённых проверках
каждый сервер получает обычный HTTP/1.1 GET с `Connection: close`; ответ `2xx`
или `3xx` считается живым. Таймаут применяется отдельно к connect, записи и
чтению.

## Крейты

| Крейт | Ответственность |
| --- | --- |
| `elira` | Бинарник, команды `run` и `check`, сигналы, `ArcSwap<Runtime>`, TCP-листенер, HTTP/1.1 и HTTP/2, metrics-листенер, PROXY protocol, graceful shutdown |
| `elira-config` | Типы TOML, `deny_unknown_fields`, валидация, ошибки загрузки; сокетов не открывает |
| `elira-proxy` | `Proxy`, `Router`, `Pool`, пересылка запросов, гигиена заголовков, retries, `CONNECT` и `Upgrade`, gzip, health-пробы, статика |
| `elira-tls` | Чтение PEM, сборка rustls-конфигурации, ALPN `h2`/`http/1.1` и `h3` для QUIC |
| `elira-accesslog` | `Entry`, текстовый и JSON-формат, экранирование, request id |
| `elira-h3` | QUIC-эндпоинт, h3-сервер, мост тела запроса, access-лог |
| `elira-metrics` | Атомарные счётчики, гистограмма, рендер Prometheus |
| `elira-limit` | Token bucket на IP, ограничение размера таблицы и очистка по idle |
| `elira-cache` | Заготовка с одним doc-комментарием; в обработке запроса не участвует |

Ключевые внешние зависимости: hyper и hyper-util для HTTP/1.1, HTTP/2 и
клиента к upstream; rustls и tokio-rustls для TLS; quinn, h3 и h3-quinn для
HTTP/3; arc-swap для подмены runtime; async-compression для gzip; ipnet для
CIDR; httpdate для дат статики.
